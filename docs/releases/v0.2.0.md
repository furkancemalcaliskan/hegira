# Hegira v0.2.0

Hegira v0.2.0 establishes the repository and workspace foundation for
maintaining the template consistently. It separates the deployable application
from reusable packages, makes current architecture and repository conventions
mechanically verifiable, and adopts source-first releases.

## Highlights

- The repository now has one canonical operating and contribution contract for
  issues, branches, commits, pull requests, integration, and releases.
- AGENTS.md-compatible tools, Codex, Claude Code, and Cursor share the same
  repository instructions through thin tool-specific adapters.
- Repository policy validates pull-request metadata, documentation links,
  agent adapters, workspace dependency boundaries, and source-first release
  invariants.
- The repository root is a virtual Cargo workspace. The deployable Axum and
  Leptos package, its entry points, integration tests, feature composition, and
  Cargo-Leptos metadata now live under `apps/hegira`.
- A locked Cargo-metadata check enforces the documented direct dependency
  boundaries and prevents reusable packages from depending on deployable
  applications.
- Full-stack validation verifies the server, database migrator, hydrated
  WebAssembly, JavaScript, CSS, and branding outputs without publishing a
  platform archive.
- Architecture, setup, deployment, operations, and maintainer documentation
  describe the resulting source tree and root-level command contract.
- GitHub Releases now distribute tagged source instead of a compiled Linux
  application bundle.

## Upgrade And Maintainer Notes

- No database migration is required.
- No runtime configuration change is required.
- Authentication, authorization, persistence, HTTP security, runtime roles,
  and deployment behavior are unchanged.
- Commands documented from the repository root continue to work. Automation
  that directly referenced the former root `src/`, `tests/`, or package
  manifest must use `apps/hegira`.
- External code contributions are not currently accepted unless explicitly
  requested or approved by the maintainer.

## Release And Supply-Chain Contract

- Create the release only from the verified `main` commit with a signed
  annotated `v0.2.0` tag.
- Keep published tags and releases immutable. Correct a released defect with a
  new patch version instead of replacing or moving the tag.
- The release workflow validates every workspace package version, the
  changelog, these release notes, the full-stack outputs, and the production
  container contract before publication.
- The workflow uses read-only repository permission except for the
  tag-triggered publication job.

## Release Artifacts

GitHub provides `.zip` and `.tar.gz` archives of the tagged source. The only
custom release asset is a source-scoped SPDX JSON SBOM containing the release
tag and commit identity.

This release does not publish a platform-specific executable, Linux application
bundle, container image, preview application, public URL, or production
deployment.

# Hegira v0.4.0

Hegira v0.4.0 consolidates the production-oriented, opinionated full-stack
application framework and introduces source-runnable application creation.
Framework packages, the official Identity module, and generated applications
now have separate ownership without the legacy compatibility host or layers.
Axum, Leptos, SQLx, and explicit ABP-inspired DDD layers remain the canonical
full-stack composition.

## Highlights

- Retired the compatibility host and legacy framework-layer packages. The root
  is a virtual framework workspace, not a deployable application.
- Moved reusable ports, persistence, background work, provider adapters,
  telemetry, and runtime support into application-independent packages.
- Removed compatibility dependencies from the official Identity Domain,
  Application, SQLx, HTTP, and Leptos packages.
- Made the canonical application own server/web composition, application DDD
  layers, configuration, migrations, seed composition, and deployment files.
- Added source-runnable `hegira new` with guided and non-interactive creation,
  SQLite/PostgreSQL selection, and the Leptos/Identity composition.
- Added a validated `hegira.toml` generation contract and a versioned,
  data-only canonical component package with a locked source digest.
- Separated deterministic rendering from repository-only dependency staging.
  Normal output pins framework dependencies to `v0.4.0`.
- Added regression coverage for guided/flag equivalence, output determinism,
  destination conflicts, unsafe paths, cancellation, and write-failure recovery.
- Aligned current documentation and package descriptions with the framework
  identity. This terminology correction is not a runtime feature.

## Create An Application From Source

From a complete v0.4.0 source checkout or extracted source archive:

```sh
cargo run --locked -p hegira_cli -- new my-application \
  --destination ../my-application
```

This selects SQLite, Leptos, and Identity. Use `--database postgres` for
PostgreSQL, or omit the name and destination in an interactive terminal for
the guided flow. Non-interactive execution requires both inputs explicitly.

Generation writes source only. It does not install dependencies, initialize
Git, run migrations, or execute the application. Keep the source tree used to
build the CLI available; the binary is not a standalone distribution. Follow
[Getting started](../getting-started.md) for prerequisites, run commands,
supported selections, destination constraints, and process outcomes.

## Ownership And Compatibility

The generated application is an independent Cargo workspace. Its `apps/server`
and `apps/web` composition roots, layered `crates/`, configuration, migration
composition, and deployment files belong to the application. Framework and
official Identity implementations remain dependencies, not copied module forks.
The generated `app_*` crate names remain brand-neutral.

`hegira.toml` records application identity, framework source/version, resolved
components, and selected adapters. It contains no runtime configuration or
secrets. Editing it does not regenerate source, change dependencies, or perform
an upgrade. Template changes do not rewrite existing applications.

This is a breaking source-layout change for consumers of the v0.3.0
compatibility host or packages. The retired `hegira`, `domain_shared`, `domain`,
`application_contracts`, `application`, `infrastructure`, `presentation`, `web`,
and `db_migrator` packages are not compatibility aliases. Existing consumers
must explicitly move application code and composition to application-owned
layers and select framework/module adapters. There is no automatic conversion.

## Database And Security Contracts

- Application infrastructure composes module migrations with preserved
  application migration history. Historical identities and checksums are not
  rewritten, including migrations for retired capabilities.
- The generated-application gate covers fresh SQLite/PostgreSQL schemas and
  the supported v0.2.0 database upgrade fixture. This is database-history
  coverage, not automatic source migration or proof for every customized schema.
- Destructive reset is restricted to explicitly authorized disposable database
  validation. Never run reset tests against persistent or production data.
- Production keeps automatic migrations and Identity seeding disabled;
  deployment automation must execute the application-owned migration plan.
- Cookie/BFF CSRF policy remains separate from Bearer API policy. Application
  services enforce authorization, and configuration/capability validation runs
  before external dependency initialization.

Back up and test restore of existing databases before migration. Review
[Architecture](../architecture.md), [Configuration](../configuration.md), and
[Operations](../operations.md) when adapting an existing application.

## Validation And Current Limits

Repository gates enforce framework/module/application dependency boundaries.
The integration gate generates both provider applications through the public
CLI, verifies their original files, and stages local framework dependencies in
separate disposable copies. It exercises native tests, hydration, release
builds, migration history, and a PostgreSQL production container with readiness,
static assets, WASM, security headers, and Bearer API checks.

Safe generation requires a new destination under an existing parent without
symlinks. It never overwrites an existing entry. Atomic publication is covered
on Linux and fails closed where the required platform primitive is unavailable.

The CLI does not provide module management, CRUD/service/controller generators,
migration commands, automatic upgrades, remote component installation, or
additional client templates. External code contributions remain restricted to
work explicitly requested or approved by the maintainer.

## Release And Supply-Chain Contract

The tag and GitHub Release title are exactly `v0.4.0`. Publish only from the
verified, promoted `main` commit using a signed annotated tag after all required
checks pass. The [maintainer workflow](../maintainers.md) defines candidate
validation, publication, and immutable-release verification.

GitHub provides source `.zip` and `.tar.gz` archives. The only custom asset is
`hegira-v0.4.0.spdx.json`, a source-scoped SPDX SBOM containing the release tag
and commit identity. GitHub's immutable-release contract supplies the release
attestation. Published tags and assets must not be moved or replaced.

All workspace packages retain `publish = false`. This release does not publish
crates, a CLI package, executable bundles, container images, preview
applications, public URLs, or deployment environments. Workflow permissions
remain read-only by default; only tag-triggered publication receives
`contents: write` after every release validation job succeeds.

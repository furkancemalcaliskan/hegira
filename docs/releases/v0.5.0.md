# Hegira v0.5.0

Hegira v0.5.0 evolves the source-runnable framework tooling from application
creation into safe inspection and deterministic modification of an existing
canonical layered application. It also introduces the first complete layered
resource generator across Domain, Application Contracts, Application, SQLx,
Axum/OpenAPI, and Leptos surfaces.

The canonical application remains a neutral starting point. No sample business
domain is added, and generated source remains explicitly application-owned.

## Highlights

- Discover and inspect an existing Hegira application from its root or a child
  directory without reading runtime configuration or changing files.
- Report application identity, framework release, selected components and
  adapters, and mutation compatibility in human-readable or versioned JSON
  output.
- Preview migration and resource changes through deterministic,
  content-redacted dry-run plans before applying them.
- Publish coordinated multi-file changes with absent-file and content-digest
  preconditions, no-follow path handling, atomic operations, rollback, and
  durable recovery state.
- Generate one typed resource across every canonical application layer while
  preserving explicit dependency, composition, authentication, and
  authorization boundaries.
- Validate generated-and-mutated SQLite and PostgreSQL applications through
  fresh and supported upgrade paths, native and hydration builds, and the
  production-container HTTP contract.
- Bound repository-owned validation build-cache growth without taking
  ownership of normal developer Cargo output.

## Inspect An Existing Application

From a generated application or any directory below its root:

```sh
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- inspect
```

Use `--application-root <path>` to select a root explicitly and `--json` for
the deterministic machine-readable output schema. Inspection reports the
manifest and mutation compatibility but performs no writes. Application-root
resolution rejects ambiguous manifests, symlinked paths, changed directories,
missing application-owned roots, malformed manifests, and inaccessible or
oversized manifest input.

The v0.5.0 mutation policy requires manifest schema `1`, the canonical Hegira
framework repository, framework version `v0.5.0`, the canonical layered Leptos
and Identity component composition, exactly one SQLite or PostgreSQL adapter,
and the Leptos client. Inspection can describe an incompatible or unsupported
application; mutation commands reject it with a conflict instead of guessing
an upgrade path.

## Safe Existing-Application Mutation

Migration and resource commands construct one typed, ordered change plan.
`--dry-run` and apply use that same plan. Human and JSON summaries expose
relative paths, operations, preconditions, and digests without exposing source
bodies, runtime configuration, credentials, or environment values.

New files must be absent. Edits carry the SHA-256 digest of the source that was
observed during planning, and publication rechecks every precondition before
changing the application. Structured editors modify only declared managed Rust
and TOML integration points and preserve unrelated application-owned content.
Missing, duplicated, reordered, occupied, malformed, or concurrently changed
integration state is a conflict rather than an overwrite.

Publication uses private staging files and an application-owned
`.hegira-mutation.lock` marker. Recoverable failures roll changes back in
reverse order. A crash, concurrent change, incomplete rollback, or uncertain
cleanup retains content-redacted recovery state and blocks later mutations for
manual inspection. Platforms and filesystems without the required no-follow
and atomic rename semantics fail before application files are modified.

## Layered Resource Generation

Generate a typed resource from an existing compatible application:

```sh
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- generate resource Order \
  --field name:string --field fulfilled_at:datetime?
```

Resource identities are UpperCamelCase. Plural names use a deterministic `s`
suffix unless supplied explicitly with `--plural`. Fields use lowercase ASCII
snake_case and the closed `string`, `bool`, `i64`, `uuid`, and `datetime`
scalar set; `?` marks nullable fields. Every resource receives a required UUID
identifier. Reserved names, source collisions, arbitrary Rust or SQL input, and
unsafe paths fail before planning.

The generated application-owned surfaces are:

- Domain: UUID entity skeleton;
- Application Contracts: commands, queries, responses, permissions, and the
  service boundary;
- Application: repository, authorization, and identifier ports plus use-case
  implementation;
- Infrastructure: the selected SQLx repository, bound queries, typed service
  composition, provider table migration, and permission seed;
- Presentation: transport-focused Axum Bearer handlers and OpenAPI
  contribution; and
- Web and server composition: Leptos pages and server functions, localization,
  routes, navigation, icons, and typed application context.

Generated application services authorize every operation before repository
access. Bearer API routes are composed separately from cookie-authenticated
browser/BFF routes. Leptos permission checks control presentation only and are
not a security boundary.

The generator handles repeatable source integration, not product design. It
does not infer aggregates, invariants, relationships, transaction requirements,
validation policy, API semantics, or user experience. Review and extend all
generated application-owned source for the product's requirements.

## Application Migration Generation

Create an append-only scaffold for the provider selected in `hegira.toml`:

```sh
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- generate migration add_orders
```

The command creates an intentionally empty SQLite or PostgreSQL SQL scaffold
and advances the application-owned generator coordination record. It never
connects to a database, executes or reverts a migration, translates SQL, or
changes historical migration contents. Complete and review the forward SQL,
then run it through the application's normal migration process.

## Validation And Compatibility Limits

The required generated-application gate creates pristine SQLite and PostgreSQL
applications through the public CLI, verifies them against the canonical
package, and mutates only disposable validation copies. It proves dry-run and
apply plan equivalence, conflict behavior, immutable historical migrations,
fresh installation, the supported v0.2.0 database upgrade, native and hydration
builds, and generated-resource authorization and CRUD behavior through the
production container.

The source-runnable CLI remains tied to the complete Hegira source checkout or
release archive used to build it. The executable is not a standalone
distribution. v0.5.0 does not provide automatic application upgrades, module
management or removal, a remote component registry, additional client
templates, runtime plugin discovery, or database migration execution.

External code contributions remain restricted to work explicitly requested or
approved by the maintainer. See [Getting started](../getting-started.md),
[Architecture](../architecture.md), and the
[maintainer workflow](../maintainers.md) for the current contracts.

## Release And Supply-Chain Contract

The tag and GitHub Release title are exactly `v0.5.0`. Publish only from the
verified, promoted `main` commit using a signed annotated tag after every
required check passes.

GitHub provides source `.zip` and `.tar.gz` archives. The only custom asset is
`hegira-v0.5.0.spdx.json`, a source-scoped SPDX SBOM containing the release tag
and commit identity. GitHub's immutable-release contract supplies the release
attestation. Published tags and assets must not be moved or replaced.

All workspace packages retain `publish = false`. This release does not publish
crates, a standalone CLI, executable bundles, container images, preview
applications, public URLs, or deployment environments. Workflow permissions
remain read-only by default; only tag-triggered publication receives
`contents: write` after all release validation jobs succeed.

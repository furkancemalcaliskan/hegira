# Hegira v0.8.0

This source preparation aligns Application Operations and Developer Workflow
Foundation on v0.8.0. It does not announce publication: promotion, signed tagging,
release validation and immutable source publication remain separate maintainer
operations. Distribution remains source-only; workspace crates are not published.

## Application Operations

The source CLI provides typed `dev`, `check`, `test`, `build --release`, and
`db status`/`db migrate` previews and explicitly trusted Linux execution.
Execution requires application trust, absolute trusted Cargo and tool selections,
profile validation and child cleanup; production migration has separate approval.
Database operations delegate to the application-owned `app_database` binary,
never provision a database, seed Identity or start HTTP. Status preserves database
data, schema and history; SQLite WAL coordination can affect sidecars.

Fresh applications receive provider-specific documentation, agent instructions,
repository policy, mandatory quality CI, and explicit operation entry points.
Generated Leptos resources support pagination. CLI validation caches have an
explicit allocated-byte budget and inactive reclamation while protecting active
leases and excluding ordinary developer output. These operations execute trusted
code and are not a sandbox.

## Direct Source Upgrade

The authenticated edge supports exactly v0.7.0 to v0.8.0 for default, minimal,
and Identity-added applications with SQLite or PostgreSQL. Review read-only
`upgrade status` and `upgrade --dry-run` before explicit apply. The plan edits
`Cargo.toml`, `Cargo.lock`, and `hegira.toml` and creates only the exact absent
`crates/infrastructure/src/database_operations.rs`.

The new source remains unregistered. The owner must review and integrate its
configuration loader, module, server binary and feature before public database
execution. Existing product code, provider/client selection, immutable migration
history, server registration, documentation and governance/CI remain preserved.
See the [manual adoption guide](../getting-started.md#adopt-database-operations-after-a-source-upgrade).

Customized managed files or occupied addition paths fail closed. Skipped or
reverse releases, provider/client switches, arbitrary merges and force upgrades
are unsupported. Preserve recovery state after interruption or uncertain rollback.
An applied receipt proves source publication only, not database or deployment
approval; review locks, run application tests and native/hydration/production
validation before operating the application.

## Source And Supply Chain

Both canonical lockfiles retain the normal v0.8.0 Git tag source and resolve
framework packages to actual merged candidate
`fd89e7ef47e064f96a2affed34076acd53c0761a`; the consumed package trees agree
with that candidate. All workspace and package identities agree on v0.8.0.
The declared target tag is not evidence of its availability before publication.
Fresh quality CI selects that same immutable published source release for its
compatible CLI catalog and verifies the checked-out local tag before bootstrap.
Existing applications review their own tool selection and security policy.

Canonical locks include reviewed security fixes without changing immutable
released baselines. The historical v0.6.0-to-v0.7.0 edge is archived byte for byte;
current lifecycle gates retain all three compositions, both providers, native,
hydration, migration preservation and production HTTP/security coverage.

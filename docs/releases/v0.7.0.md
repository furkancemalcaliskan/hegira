# Hegira v0.7.0

This is a pre-tag source candidate. No v0.7.0 tag or GitHub Release has been
published.

The current source checkout aligns framework, official-module, tooling,
component-package, and canonical application identities to v0.7.0. Default
and minimal application lockfiles retain the normal release-tag Git source
and resolve it to the reviewed #350 candidate revision.

The immutable v0.6.0 application baselines remain unchanged. The package now
declares a data-only upgrade edge for default, minimal, and Identity-added
SQLite/PostgreSQL applications. The public CLI exposes read-only `upgrade status`
and reviewable `upgrade --dry-run` with authenticated readiness, plus `upgrade`
for atomic application of the same typed plan with deterministic receipts and
explicit application-owner next steps. Committed JSON schemas, reviewed
human/JSON snapshots, and typed diagnostics/process-outcome tests stabilize
the upgrade automation contract. A shared public-process matrix verifies readiness,
preview, apply, repeat rejection, inspection, doctor compatibility, and protected
resource capability gating across all six supported released compositions. The
layered-template gate compiles each customized public-upgrade result for native
and WASM hydration in separate local-source validation staging. A dedicated
released-application lifecycle validator exercises fresh and v0.6.0 upgrade
databases, migration history and product-data preservation, release assets, and
production container HTTP/security contracts across both providers and all three
compositions. Final release notes and the release date are verified during
release preparation.

## Frontend Security Verification

Canonical frontend build tooling keeps Tailwind unchanged while replacing its
watcher dependency with the reviewed 2.6.0 release. This removes the vulnerable
`micromatch`/`braces` chain associated with the public upstream advisory
[GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm).
Supply-chain and release validation audit both canonical npm lockfiles and
fail on high or critical findings.

Existing applications retain application-owned frontend manifests and locks
during upgrade. Their owners must separately review and apply the
[frontend dependency remediation](../getting-started.md#frontend-dependency-remediation);
the authenticated upgrade edge and immutable v0.6.0 baselines are unchanged.

The finding identified during candidate review was resolved by #367. Both
canonical npm graphs omit `micromatch` and `braces`; repeat audit of all
dependency classes reported zero vulnerabilities. Clean npm installation,
Tailwind CSS generation and native watcher compatibility were checked, and
audit failure propagation is enforced by policy and process tests. This does
not assert that preserved application-owned frontend dependencies in existing
applications have been remediated automatically.

## Upgrade And Publication Boundaries

The only supported direct transition is v0.6.0 → v0.7.0 for default, minimal,
and Identity-added applications using SQLite or PostgreSQL with Leptos. It edits
only `Cargo.toml`, `Cargo.lock`, and `hegira.toml`. Customized managed files fail
closed; application-owned product code, generated-once scaffolding, runtime
configuration, and immutable migration history are preserved. There is no
arbitrary source merge, skipped-release upgrade, downgrade, provider/client
switch, component removal, or automatic database migration/deployment.

Review [readiness and execution](../getting-started.md#assess-application-upgrade-readiness),
[post-upgrade responsibilities](../getting-started.md#after-an-application-upgrade),
and [conflict/recovery guidance](../getting-started.md#resolve-upgrade-conflicts-and-recovery)
before upgrading an application. An applied receipt proves source publication,
not production readiness.

This candidate does not publish a tag, Release, crate, executable, container
image, or preview environment. Final release preparation owns the completed
CHANGELOG and publication notes, verified `develop` → `main` promotion, signed
annotated `v0.7.0` tag, source-only GitHub Release titled exactly `v0.7.0`, SPDX
SBOM, and publication verification. Every Required milestone issue and required
check must pass before the public tag is created; the milestone remains open
until publication verification succeeds.

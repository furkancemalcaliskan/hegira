# Hegira v0.7.0

Hegira v0.7.0 adds the first supported existing-application upgrade lifecycle.
Applications created with v0.6.0 can assess readiness, review an authenticated
plan, and apply a direct v0.7.0 source transition without silently overwriting
product code or migration history.

This release also gives repository-owned validation artifacts a bounded cache
lifecycle and makes fresh and upgraded application validation parallel without
reducing provider, hydration, migration, or production coverage. Hegira remains
a source-oriented, opinionated application framework with explicit composition
and application-owned product development.

## Highlights

- Record exact release state and source ownership in schema-3 `hegira.toml`.
- Authenticate data-only direct upgrade edges, immutable released baselines,
  supported compositions, and managed source before planning a transition.
- Assess readiness with read-only `hegira upgrade status`.
- Review a deterministic, content-redacted plan with `hegira upgrade --dry-run`.
- Apply the same typed plan through the atomic mutation and recovery boundary
  with a versioned source-publication receipt.
- Upgrade default, minimal, and Identity-added v0.6.0 applications using SQLite
  or PostgreSQL while preserving their selected client and composition.
- Stabilize upgrade automation with committed JSON schemas, reviewed output
  snapshots, typed diagnostics, and tested process outcomes.
- Bound repository validation caches under a configurable 64 GiB default LRU
  budget while protecting active checks and normal developer output.
- Require all five fresh and released-upgrade lifecycle cells in the aggregate
  quality gate.
- Remove the vulnerable canonical frontend `micromatch`/`braces` chain without
  downgrading Tailwind, and audit both canonical npm lockfiles in CI and release
  validation.

## Source Ownership And Upgrade Plans

Schema-3 application manifests distinguish application-owned source, managed
integration points, generated-once scaffolding, and immutable history.
Unclaimed paths remain application-owned. A managed claim is not blanket
permission to rewrite a file: the authenticated edge and observed source
digests must authorize each transition.

The bundled package declares an exact, data-only v0.6.0 to v0.7.0 direct edge.
Package loading authenticates source through directory-anchored no-follow reads
and a digest-verified snapshot. Immutable, content-addressed application
baselines cover all six supported composition/provider states without consulting
current templates, Git, or the network.

One typed plan coordinates framework dependencies, component-package identity,
installed components, and application-manifest state. Its versioned summary
records release identities, ownership, integration points, ordered operations,
and source/result digests without exposing file contents or secrets.

The mutation publisher now supports exact-digest managed-file retirement with
private rollback staging. Retirement cannot target application-owned,
generated-once, or immutable-history source. The bundled application upgrade
uses edits only; it retires no files and changes exactly:

- `Cargo.toml`
- `Cargo.lock`
- `hegira.toml`

Product customizations outside those managed files, runtime configuration,
frontend dependency files, and historical migration bytes remain untouched.
See the [ownership contract](../getting-started.md#generated-ownership-and-hegiratoml)
and [architecture](../architecture.md) for the implemented boundaries.

## Supported Application Upgrades

| Released v0.6.0 composition | Databases | v0.7.0 result |
| --- | --- | --- |
| Default Identity | SQLite, PostgreSQL | Identity and authentication/authorization retained |
| Minimal | SQLite, PostgreSQL | Module-free application; no Identity, login, or protected resource generation |
| Minimal plus installed Identity | SQLite, PostgreSQL | Installed Identity integrations and capabilities retained |

All six transitions retain the application identity, selected database and
Leptos client. Existing v0.7.0 applications have no outgoing bundled edge:
readiness and preview report `no-upgrade`, while apply is unsupported and writes
nothing.

Use the target v0.7.0 source checkout or complete source release archive, not
the application's old v0.6.0 CLI. From the application root, first assess and
preview:

```sh
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- upgrade status --json
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- upgrade --dry-run --json
```

Omit `--json` for human-readable output. Review the plan, back up the application
and database, and stop competing source mutations before explicitly applying:

```sh
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- upgrade --target v0.7.0 --json
```

Readiness and preview perform no source writes, database operations, network
access, or subprocess execution. A successful preview is an observation, not a
cached publication token. Apply reauthenticates source, recomputes the typed
plan, serializes publication with an application-owned recovery marker, and
enforces digest preconditions before and during publication.

## Conflicts, Recovery, And Automation

Customized managed files, unsupported release states, composition mismatches,
unsafe paths, concurrent changes, and incomplete recovery fail closed. Hegira
does not merge arbitrary modifications or provide a force-upgrade option.
Recoverable publication failures roll back staged source changes; interruption
or uncertain rollback preserves recovery information and blocks later mutation.

Preserve `.hegira-mutation.lock` and private staged files until a verified
consistent state is restored. Do not remove a marker just to retry. If output
delivery fails after publication, inspect source and recovery state before
assuming the upgrade did not apply.

Upgrade status and execution expose schema-1, content-redacted JSON on stdout.
Unsupported or incompatible requests exit 3, source or recovery conflicts exit
4, parser errors exit 2, and internal/publication errors exit 1. Applying the
same upgrade again exits 3 without a second mutation. Committed
[status](../../tools/hegira_cli/schemas/upgrade-status-v1.schema.json) and
[execution](../../tools/hegira_cli/schemas/upgrade-execution-v1.schema.json)
schemas, human/JSON snapshots, and public-process tests enforce this contract.

See [readiness and execution](../getting-started.md#assess-application-upgrade-readiness)
and [manual conflict/recovery guidance](../getting-started.md#resolve-upgrade-conflicts-and-recovery)
before automating an upgrade.

## Application-Owner Responsibilities

An applied receipt proves source publication, not production readiness. Before
running or deploying the upgraded application:

1. Review the three-file diff, receipt, exact target identity, and preserved
   application composition.
2. Review the authenticated lockfile and keep locked builds. Do not regenerate
   dependencies merely to hide a conflict.
3. Review pending migrations and execute them through the application's normal
   backed-up operation workflow. Source upgrade executes no SQL.
4. Run application tests, selected-provider native and hydration checks, and
   production/security validation.
5. Deploy only after those checks succeed. Source rollback does not restore a
   database or a running deployment.

Canonical frontend tooling uses a scoped `@parcel/watcher` 2.6.0 override to
remove the vulnerable `micromatch`/`braces` chain while retaining Tailwind.
Existing applications own their frontend manifests and locks; this source
upgrade does not remediate them automatically. Review and apply the separate
[frontend dependency remediation](../getting-started.md#frontend-dependency-remediation)
and [post-upgrade checks](../getting-started.md#after-an-application-upgrade).

## Bounded Build Artifacts And Validation

Supported repository validators use stable, locked workspaces and separate
build caches below `target/validation/`. Incremental compilation and development
and test debug information are disabled only for validation. Preparation and
release prune least-recently-used inactive caches under the 65,536 MiB default
budget; `HEGIRA_VALIDATION_CACHE_MAX_MIB` can select another positive budget.

Active locks protect in-flight checks. If protected or shared state alone
exceeds the budget, validation stops rather than deleting active state or
continuing uncontrolled growth. The budget does not cover normal developer
Cargo output, global Cargo caches, or Docker storage, which are not silently
deleted. A representative equivalent warm framework check demonstrated zero
second-run cache growth. Inspect current usage without removing anything:

```sh
sh scripts/clean-validation-cache.sh --status
sh scripts/clean-validation-cache.sh --prune-dry-run
```

See the [maintainer cache lifecycle](../maintainers.md#validation-build-cache-lifecycle)
for ownership, measurements, and cleanup commands.

Generated release tooling selects wasm-bindgen from the reviewed application
lockfile and verifies its installed version. Repository CI runs five isolated
application lifecycle cells in parallel: `default`, `identity-added`,
`upgrade-default`, `upgrade-minimal`, and `upgrade-identity-added`. Each relevant
cell covers both providers; `quality` requires all cells and its framework,
official-module, tooling, feature-matrix, and supply-chain owners.

Released-upgrade validation exercises public readiness, preview, apply, repeat
rejection, inspection, doctor, protected-resource capability gating, customized
product-source preservation, migration checksums and existing data, native and
hydration builds, and production-container HTTP/security behavior. Disposable
databases, containers, and generated images retain explicit cleanup lifecycles.

## Compatibility And Current Limits

The only bundled direct upgrade is v0.6.0 to v0.7.0 for the six supported Leptos
states above. Customized managed files, skipped releases, downgrades,
database/client switches, arbitrary component graphs, and automatic conflict
merges are unsupported. Managed retirement is a constrained tooling operation,
not public component or module removal.

Default generation still selects Leptos, Identity, and SQLite; PostgreSQL and
the module-free minimal composition remain explicit choices. Hegira does not
provide automatic migration execution, deployment orchestration, a remote
component registry, runtime plugin discovery, or additional client templates.
The CLI still runs from a complete source checkout or release archive; no
crates.io package or standalone executable is published. External code
contributions remain restricted to maintainer-requested or approved work.

## Release And Supply-Chain Contract

Framework, official-module, tooling, canonical package, template, and
application identities agree on v0.7.0. Default and minimal Cargo lockfiles keep
the release-tag Git source and pin consumed framework packages to reviewed
revision `7a9ed5bce734f5459fee62d3a2069ce1cfc7d212`. That dependency revision is
distinct from the complete promoted release commit; publication does not move
the pin or rewrite authenticated upgrade targets.

The tag and GitHub Release title are exactly `v0.7.0`. Publish only from the
verified, promoted `main` commit using a signed annotated tag after every
required milestone and CI gate and the manual release-candidate workflow
succeed. Earlier candidate checks do not approve a different release commit.

GitHub provides source `.zip` and `.tar.gz` archives. The only custom asset is
`hegira-v0.7.0.spdx.json`, a source-scoped SPDX SBOM containing the release tag
and commit identity. GitHub's immutable-release contract supplies the release
attestation. Published tags and assets must not be moved or replaced; close the
milestone only after publication verification succeeds.

All workspace packages retain `publish = false`. This release does not publish
crates, executable bundles, container images, preview applications, public URLs,
or deployment environments. Workflow permissions remain read-only by default;
only tag-triggered publication receives `contents: write` after every required
validation job succeeds. See the [release contract](../maintainers.md#release-contract)
for promotion, candidate validation, and immutable-release verification.

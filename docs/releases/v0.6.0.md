# Hegira v0.6.0

Hegira v0.6.0 introduces an explicit component-composition model and the first
safe additive lifecycle for an official module. The recommended application
still starts with Leptos, Identity, and SQLite by default, while an explicitly
selected minimal application can now begin without Identity and install it
later through the same typed composition contract.

This release keeps Hegira source-oriented and deliberately bounded. Components
are generation and installation units, official modules remain versioned
layered framework packages, and generated applications continue to own their
composition roots and product source.

## Highlights

- Record the resolved component package, components, official modules,
  capabilities, database provider, and client in a schema-2 `hegira.toml`.
- Resolve a closed component graph deterministically, including exact versions,
  required and optional dependencies, conflicts, capabilities, and official
  module ownership.
- Create the recommended Identity application by default or explicitly select a
  module-free minimal composition.
- Inspect composition status in human-readable or versioned JSON form.
- Preview and atomically apply the official Identity component to a compatible
  minimal application.
- Diagnose composition, recovery, managed integration points, and local
  development prerequisites without modifying the application.
- Reject protected resource generation until authentication and authorization
  capabilities are present.
- Generate applications with a release-reviewed canonical Cargo lockfile.
- Validate default, minimal, and Identity-added applications across SQLite,
  PostgreSQL, native, hydration, development, migration, and production
  container contracts.

## Composition And Ownership

The component package is a release-aligned, data-only catalog. Each component is
a typed graph node that contributes source during initial generation or
describes one additive installation unit. An official module is different: it
is reusable layered framework source under `modules/`, with explicit Domain,
Application, provider, HTTP, and client adapters where applicable.

The default `identity` composition resolves `layered-base` and
`layered-leptos-identity`. It records the official Identity module and the
`authentication` and `authorization` capabilities. This remains the default
for `hegira new`.

The explicit `minimal` composition resolves `layered-base` and
`layered-leptos-minimal`. It retains the layered application, Axum host,
Leptos client, selected SQLx provider, configuration, migrations, and
deployment files but records no official module or authentication and
authorization capability. It does not substitute anonymous or allow-all
authorization.

Create a minimal SQLite application from a complete v0.6.0 source checkout or
source archive:

```sh
cargo run --locked -p hegira_cli -- new minimal-app \
  --destination ../minimal-app \
  --composition minimal
```

Use `--database postgres` to select PostgreSQL explicitly. Normal generation
retains release-pinned framework sources and the canonical dependency lockfile.

## Inspect And Diagnose

From an application root or a directory below it, inspect the recorded and
resolved composition:

```sh
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- inspect
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- doctor
```

`inspect` reports application identity, framework and package versions,
components, modules, capabilities, selected adapters, graph diagnostics, and
mutation compatibility. `doctor` additionally checks recovery state, managed
integration points, and local prerequisites. Both commands are read-only and
support `--json` for their versioned machine-readable contracts.

Application discovery rejects ambiguous manifests, symlinked paths, missing
owned roots, malformed input, and inaccessible or oversized manifests.
Diagnostics remain content-redacted and do not read runtime credentials or
probe external databases.

## Add The Official Identity Module

The default application already contains Identity. For a compatible minimal
application, review the installation plan before applying it:

```sh
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- component add identity --dry-run
cargo run --locked --manifest-path /path/to/hegira/Cargo.toml \
  -p hegira_cli -- component add identity
```

Dry-run and apply use the same typed, ordered, content-redacted mutation plan.
The Identity installation unit contributes release-pinned layered
dependencies, selected-provider migration sources, configuration and seed
composition, background work, cookie/BFF and Bearer routes, OpenAPI, Leptos
routes, and navigation through declared managed integration points. It
references the official module packages; it does not vendor or copy their
source into the application.

Publication uses absent-file and digest preconditions, no-follow path handling,
private staging, atomic replacement, reverse rollback, and an
application-owned recovery marker. Occupied paths, stale files, concurrent
changes, incompatible composition, unsupported adapters, unsafe filesystem
semantics, or incomplete recovery fail without overwriting application-owned
source. A repeated installation is a non-destructive conflict.

After installation, the application owner must:

1. Review the selected runtime configuration and keep secrets environment
   backed.
2. Run `cargo generate-lockfile` and review the application-owned dependency
   change.
3. Apply the selected provider's application-owned migration plan through the
   normal deployment process.
4. Format and validate the complete application.
5. Run `inspect` and `doctor` again.

The CLI does not connect to the database or execute migrations during component
installation.

## Capability-Gated Resource Generation

Generated resources retain application-layer authorization for every use case.
The resource generator now verifies the resolved composition before planning
protected Domain, Application, SQLx, Axum/OpenAPI, and Leptos surfaces.

A minimal application without Identity fails closed because it lacks
`authentication` and `authorization`. After the complete Identity
installation succeeds, the same application can generate protected resources
through its minimal shell while preserving the application service security
boundary. Presentation permission checks remain user-interface behavior and do
not replace application authorization.

## Reproducible Generation And Validation

Each default and minimal application receives a canonical `Cargo.lock` whose
framework git packages use the v0.6.0 release source and one reviewed precise
revision. SQLite and PostgreSQL generation receive byte-identical dependency
locks. Application owners may intentionally update dependencies later; Hegira
does not silently update an existing application.

Repository validation verifies public CLI output before staging local framework
dependencies in disposable copies. Required gates cover deterministic
generation, dry-run/apply equivalence, installation conflicts and recovery,
capability rejection and enablement, fresh and supported database upgrades,
native and hydration targets, the documented non-release Cargo Leptos build,
production images, security headers, authentication, authorization, and
generated-resource CRUD for both providers.

## Compatibility And Current Limits

The v0.6.0 mutation policy requires schema `2`, the canonical framework and
component package identity, exact v0.6.0 versions, a supported default or
minimal composition, one SQLite or PostgreSQL provider, and the Leptos client.
v0.5.0 manifests remain readable for inspection but are not automatically
upgraded or mutable. Changing a framework release, database, client, or
customized integration remains an explicit application-owned operation.

This release does not provide component or module removal, automatic framework
or application upgrades, migration execution, a remote package registry,
untrusted third-party installation, independent official-module versioning,
runtime plugin discovery, or additional client templates.

The source-runnable CLI still requires a complete Hegira source checkout or
release archive. There is no crates.io package or standalone executable.
External code contributions remain restricted to work explicitly requested or
approved by the maintainer.

## Release And Supply-Chain Contract

The tag and GitHub Release title are exactly `v0.6.0`. Publish only from the
verified, promoted `main` commit using a signed annotated tag after every
required check and the manual release-candidate workflow succeed.

GitHub provides source `.zip` and `.tar.gz` archives. The only custom asset
is `hegira-v0.6.0.spdx.json`, a source-scoped SPDX SBOM containing the release
tag and commit identity. GitHub's immutable-release contract supplies the
release attestation. Published tags and assets must not be moved or replaced.

All workspace packages retain `publish = false`. This release does not publish
crates, a standalone CLI, executable bundles, container images, preview
applications, public URLs, or deployment environments. Workflow permissions
remain read-only by default; only tag-triggered publication receives
`contents: write` after every validation job succeeds.
